# AGENTS.md — robotctl project guide

Quick-start context for coding agents. Do not rebuild from scratch; this file + focused reads are enough.

## What this is
Universal robot controller, headless REST API. `POST /commands` takes natural language (or manual `/do …`) → LLM proposes a plan **in the robot's own command language** → safety layer validates against the uploaded robot profile → executor forwards each step to the real robot's HTTP endpoints. The core is robot-agnostic: ALL robot knowledge (actions, params, limits, example answers) comes from a profile JSON uploaded via `POST /profile` — nothing hardcoded. No simulation (mock adapter deleted), no interactive CLI, no web view (all removed by user request). The robot exposes `GET /telemetry`, `POST /command`, `POST /stop` (contract in `API_README.md`); its companion app is the user's to build. Loopback-only, docs disabled.

## Commands (project root, WSL2; always `uv`, never pip)
- `uv sync` — install deps
- `uv run pytest -q` — full suite (~40 s, 137 tests)
- `uv run robotctl` — API service on 127.0.0.1:8081 (foreground; `--host`/`--port`; Ctrl+C/SIGTERM safe stop). Boots fine with no robot (`ROBOT_BASE_URL` empty): `/health` ok:false, execution fails safely.

## Architecture (src/robotctl/ — 3 moduły + __init__ z re-eksportami)
- `core.py` — contracts + validation, robot-agnostic. Składa się (w tej kolejności) z: **schemas** (uniwersalna koperta: `PlanResponse{version=1, mode: action|plan|clarification, steps[], question, options}`, `extra="forbid"`; kroki to `ActionStep{action: str}` z `extra="allow"` — params definiuje profil, waliduje safety, NIE koperta; `Telemetry`: wymagane tylko timestamp/monotonic/connected/motion_status, reszta opcjonalna; `describe_step()` generic), **config** (pydantic-settings czyta `.env`: `max_plan_steps`, `step_timeout_s`, `telemetry_max_age_s`, `risky_actions` (NoDecode + CSV; pusta nie może crashować), robot bridge: `robot_base_url` (puste = brak robota, fails safe), `robot_command_path`/`robot_telemetry_path`/`robot_stop_path`, `robot_timeout_s`, `robot_poll_hz`, `profile_path`), **profile** (THE robot-specific contract: `RobotProfile{profile_version, robot{name,description}, actions[{action, description, params[{name,type(int|float|str|bool),unit,min,max,required,default}]}], examples[]}`; `examples` muszą być dokładnie poprawnymi odpowiedziami w uniwersalnej kopercie, walidowanymi przeciw `actions` (odrzucane przy uploadzie inaczej) — wstrzykiwane verbatim do promptu LLM; `check_step()` waliduje/normalizuje krok (nieznane action/param, typ, min/max; wypełnia defaulty); `response_schema()` buduje strict structured-output schemę dynamicznie per profil; `ProfileManager` trzyma bieżący profil, persistuje do `PROFILE_PATH`, przeładowuje przy starcie (corrupt → warn, dalej bez profilu); `parse_do_action(args, profile)` = pozycyjne parsowanie `/do`) oraz **safety** (deterministyczna bramka: reguły koperty (action⇒1 krok, długość planu), każdy krok przez `profile.check_step()`; `requires_confirmation()` matchuje nazwy akcji z `RISKY_ACTIONS`).
- `runtime.py` — execution engine. Składa się z: **adapter interface** (`RobotAdapter` ABC connect/disconnect/execute/stop/telemetry; `execute` musi haltować ruch przy CancelledError), **HTTP bridge** (`HttpRobotAdapter` — JEDYNY adapter: generic HTTP bridge; `connect()` startuje poll task (`robot_poll_hz`, default 5 Hz) GETujący telemetry endpoint i mapujący na uniwersalne `Telemetry` (nieznany `motion_status` → "error"; brakujące pola → None; toleruje 3 kolejne nieudane polle, potem connected=False i snapshot `connected: false, motion_status: "error"`); `execute()` POSTuje zwalidowany step JSON do command endpoint; robot odpowiada po zakończeniu — 2xx ok, 4xx/5xx lub body `ok:false`/`status: failed|error` → `AdapterError`; CancelledError → best-effort `POST /stop` przed re-raise; `stop()` best-effort, nigdy nie rzuca; przyjmuje opcjonalny `transport` (httpx.AsyncBaseTransport) do testów; brak `ROBOT_BASE_URL` → pozostaje rozłączony, execution fails safe), **monitor** (`StateMonitor`: telemetry snapshot + freshness (`telemetry_max_age_s`) + history deque), **planner** (`LLMPlanner`: `AsyncOpenAI` → configurable endpoint; system prompt budowany per call z bieżącego profilu (nazwa/opis robota, słownik akcji z limitami, examples verbatim, zasada split-don't-ask); json_schema response_format generowany z profilu; łańcuch fallbacków json_schema → json_object → none (2 próby każdy); auto-zrzuca `LLM_EXTRA_BODY` jeśli odrzucony; wycina think-blocki + łapie `reasoning_content`; `parse_plan_response(content, profile)` dodatkowo waliduje kroki przeciw profilowi, żeby pętla retry auto-korygowała nieznane/nieprawidłowe akcje; przenosi nierozwiązane clarifications do następnej komendy (`_pending_clarification`, ograniczona historia, przywracane przy nieudanych próbach, czyszczone po rozwiązaniu); `LLMInteraction` deque + JSONL w `LLM_LOG_FILE`; `entries()` zasilają `GET /logs`; bez profilu rzuca `PlannerError("no robot profile loaded…")`) oraz **executor** (`Executor`: jedna komenda naraz (`ExecutorBusy`); `submit()` (przez LLM) i `submit_plan()` (pomija LLM, używane przez `/do`); konstruktor `(settings, adapter, monitor, planner, profiles)`; kroki pod `wait_for` timeout ze świeżą telemetrią między krokami; failure → safe stop + status terminalny; e-stop połyka cancellation → status `stopped`, adapter haltowany bezpośrednio; bez profilu komenda `rejected`).
- `service.py` — REST API + entry point. **api**: `create_app` — jedyne miejsce kontaktu z aplikacją. `POST /profile` (walidacja przez `parse_profile`, 422 + powód przy błędzie; persistuje + hot-apply), `GET /profile` (404 gdy brak), `POST /commands` (202; 409 busy; 422 bez profilu lub przy złym `/do`; body `{command, confirm}` — ryzykowne plany odrzucone bez `"confirm": true`), `GET /commands/{id}`, `GET /state` (503 bez telemetrii), `GET /logs?limit=N` (duck-typed planner `entries()`), `POST /stop`, `GET /health{ok, adapter:"http", robot_configured, profile_loaded}`. **entry point**: `main()` (`robotctl` script → `service:main`): buduje HttpRobotAdapter+monitor+profiles+planner+executor, uruchamia uvicorn na TYM SAMYM pętli asyncio (`await server.serve()`; uvicorn obsługuje SIGINT/SIGTERM), bezpieczny teardown w `finally`. NIE przerywa gdy robot nieosiągalny — warnuje i serwuje. Żadnego kodu UI.

## Tests (tests/)
- conftest `settings` fixture: `_env_file=None`, `profile_path=""`, prompt-only LLM format, no log file, step_timeout 5 s / telemetry age 2 s — generous margins because drvfs stalls; tests that exercise timeouts/staleness override these.
- `helpers.py`: `make_profile()` (move/turn/wait profile with an example), `make_profiles()`, `step()`, `action_plan`/`multi_plan` (dicts coerce to ActionStep), `FakePlanner`, `FakeAdapter` (records executed steps; `fail_on`/`hang_on`/`execute_delay_s`/`drop_link()` controls; `executed`/`halted`/`stops` assertions), `stack()` (adapter+profiles+monitor+executor with teardown), `wait_for_status()`.
- `test_profile.py` profile validation/examples/check_step/schema/manager/`/do`; `test_http_adapter.py` the bridge against `httpx.MockTransport` (injected via `HttpRobotAdapter(settings, transport=…)`); `test_planner.py` uses `FakeClient`/`FakeCompletions` (str content, `(content, reasoning_content)` tuple, or Exception) + `make_profiles()`; `test_api.py` in-process via httpx `ASGITransport`, `app_client()` helper builds `create_app(executor, monitor, settings, planner, profiles)`.
- Verified against the real endpoint (psnc HPC, Qwen3.8-27B): uploaded a crane profile (lift/lower/slew), NL command "lift the hook half a meter then turn 90 degrees" → plan `[{"action":"lift","meters":0.5},{"action":"slew","degrees":90}]` in 1 attempt. Execution correctly failed safe (no robot).

## Environment gotchas (WSL2, project on /mnt/c → NTFS/drvfs)
- Stale `__pycache__` after edits causes bizarre behavior: `find . -name __pycache__ -type d -prune -exec rm -rf {} +`
- Port 8080 is occupied by another service here → API default is 8081.
- In the agent sandbox, cross-process networking fails (curl → background server refused); verify HTTP in-process (ASGITransport / urllib from a thread — threads share the loopback namespace, cross-thread probes work).
- Literal think tags written through tool calls can get stripped — build them by string concat (`"<" + "think>"`). Same trick for f-strings: Python 3.12 chokes on `f'{{"x": "{expr}"'` inside list displays ("unmatched ']'" SyntaxError) — build such strings by concatenation instead.
- `httpx.MockTransport` handlers are awaited but do NOT enforce client timeouts — don't write timeout tests against it (test ConnectError paths instead).
- Load spikes can stall the event loop for seconds: keep generous wall-clock margins in tests.
- `os._exit(0)` in probe scripts skips stdout flushing — run `python -u` or print with flush.

## Hard rules
- The core must stay robot-agnostic: never hardcode actions; all robot knowledge flows from the profile.
- LLM output is never trusted: planner parses (+ profile re-check) → safety validates → executor controls; e-stop bypasses the LLM.
- No motion without a reachable robot: `ROBOT_BASE_URL` empty or telemetry dead → execution fails safe.
- No `git commit`/`push` — the user handles version control.
- Keep prompts small, responses JSON-only; `LLM_TEMPERATURE=0`.
